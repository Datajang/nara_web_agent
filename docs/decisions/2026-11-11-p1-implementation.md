# P1 구현 중 정한 것과 확인한 것
- 명세 위치: §4, §5, §12.3, §13.3
- 결과·결정:
  - DB: 개발·테스트는 Docker `postgres:16`(127.0.0.1:5433, 볼륨 `nara-pg16`). 시스템 PG 13(5432)은 건드리지 않음. 운영 DB 배치는 P4
  - §5.4 [미확인] 한글 trigram: en_US.utf8 로케일에서 `ILIKE '%민원분석%'`가 `ix_bids_title_trgm`을 탐(EXPLAIN 테스트로 고정). 로케일 재생성 불필요
  - `bid_files.attempts` 열 추가: §5.1 "failed는 24시간 뒤 최대 3회 재시도"에 필요하나 §4 표에 없음
  - 커버리지 판정에 1시간 여유(FRESHNESS) [가정]: incremental 주기 사이 몇 분 늦은 covered_to 때문에 매 검색이 fill을 부르지 않게
  - fill은 최근 쪽 빈 구간부터, 커버리지 경계에서 바깥쪽으로 채움(연속 구간 유지). 31일·40회 상한
  - 점수(`bid_scores`)에는 single-flight를 걸지 않음: upsert가 경쟁을 흡수, 최악은 중복 LLM 호출 1회. §5.5 표와 다름 → P3에서 재검토
  - LLM은 P1에서 인터페이스(`app/llm/base.py`)와 가짜만. 캐시 계약(요약·분석·점수)과 b-ID 참조(규칙 6)까지 구현. 실제 프롬프트·스키마는 P3
  - 검색 CLI(`python -m app.search`)는 사용자 없이 돌아 스냅샷 없이 usage_logs만 남김. HTTP API는 P2·P3
  - 허용 호스트 검사는 다운로더 안과 `files/store.py` 양쪽에서(어떤 다운로더를 주입해도 SSRF 방지)
  - **보안 사고(로컬)**: 수집기 CLI의 INFO 로그에 httpx가 요청 URL 전체(서비스키 포함)를 찍음. 저장소 밖 임시 로그에만 남았고 즉시 삭제. `app/logging_setup.py`로 httpx 로그 억제 + `ServiceKey=` 마스킹 필터, 회귀 테스트 추가
- 실측(실제 G2B): backfill 90일 = 181회 호출, 일반공고 38,820행 → 34,465건(차수 중복), 사전규격 17,712건, DB 247MB. 커버리지 밖 10일 fill 검색이 71초 걸림(첫 사용자가 오래 기다림)
