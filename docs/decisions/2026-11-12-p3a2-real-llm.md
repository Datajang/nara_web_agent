# P3a-2 실제 모델 검증 (골든셋 초안 19건)
- 명세 위치: §8.1 표·§8.1-1 스키마 우선, §8.8-1·2·4·5, §12.4·§12.5
- 질문: 실제 vLLM(Qwen3.5-9B FP8, 0.19.1, L4)에서 요약·분석이 수용 기준을 넘는가
- 방법: `eval/run_eval.py run --label <이름> --injection 3` (개발 DB, 운영 파이프라인 그대로, `llm_model_id`에 `-eval-<이름>`을 붙여 캐시 분리). 결과 `eval/results/2026-11-12_eval_<이름>.json`
- 결과(v1, `fp8`): 19/19 완료 2,795초. 스키마 첫 시도 96.4%·repair 후 98.6%(generate 138회). 숫자·날짜 원문 일치 85.9%(목표 95%). 인젝션 3/3 무시(스키마·예산·날짜 동일). 점수-라벨 Spearman 0.66(배치)·0.31(분석), P@5 0.2(초안 라벨). **요약의 일정·예산·요구사항·자격·평가가 19건 모두 비어 있음**
- 원인: 기본값 있는 필드는 JSON 스키마에서 선택(required 아님)이라, 강제 디코딩에서 모델이 필드를 통째로 뺀다. 같은 문서로 map 비교: 기본 스키마 79토큰(doc_type·risks만), 모두 required면 내용을 채우지만 2,000토큰에서 잘림(finish=length). 한도 4,000에서 4건 출력 1,043~2,113토큰, 모두 검증 통과(요구사항 5~20개)
- 결정(구현):
  - `structured.strict_schema()`: 모델에 보내는 스키마만 모든 필드 required. Pydantic 검증 스키마는 그대로(null·빈 목록 허용)
  - `summarize_file`·`summarize_bid` 최대 출력 2,000·2,500 → 4,000(§8.3 출력 예산과 같음). 점수·분석 스키마는 원래 모두 required라 그대로
  - `LLM_TIMEOUT_S` 기본 180 → 360: 동시 3~4요청일 때 요청당 17~22토큰/초(vLLM 로그)라 4,000토큰 출력이 200~235초. 180이면 타임아웃 뒤 재시도가 같은 생성을 처음부터 반복함(첫 v2b 실행 31분 동안 재시도 16회)
  - `PROMPT_VERSION` v1 → v2(캐시 분리). 평가 지표에 구조화 필드 채움 수 `filled` 추가
- 결과(v2, `fp8-v2b`): 구조화 필드 채움 일정 19·예산 19·요구사항 19·자격 16·평가 17(v1은 모두 0). 원문 일치 93.7%(v1 85.9%). 예산 추출 12/19(v1 0), 계약 방식 4/14, 마감일 0/16(라벨·지표 확인 필요). Spearman 0.73(배치)·0.39(분석), P@5 0.6(v1 0.2). 인젝션 3/3 무시이나 g001 예산이 달라짐. **스키마 첫 시도 73.2%·repair 후 92.7%(generate 123회, 최종 실패 9회)로 v1(96.4%·98.6%)보다 나빠짐** — 모든 필드를 채우게 하면서 생긴 형식 오류. 원인 분석·수정은 다음 작업
- 초안 라벨 주의: `expect.budget_won`은 G2B 추정가격(부가세 제외)이라 원문 사업비와 다름(예: g012 45,454,545 vs 50,000,000). `expect.method`는 계약 방식이라 평가 방식과 다를 수 있음. 분석 적합도 점수가 85에 몰림 → 라벨 확정 후 다시 판단
- 명세 수정: 2026-11-12 사용자 승인, Claude Docs 원본에 반영 — §8.1 표 map·reduce 출력 4,000, §8.1-1에 "모델에 보내는 스키마는 모든 필드 required" 추가, §8.2 `LLM_TIMEOUT_S`(읽기 180 → 360)
- 잘림 원인(2026-11-12~13): 같은 25청크를 다시 돌려 summarize_file 실패 9/25가 **모두 4,000토큰 finish=length**(형식·검증 오류 0)임을 확인. 모델이 요구사항 29개+·text와 evidence에 같은 문장을 두 번 씀. 잘린 출력을 되돌려 보내는 repair는 같은 길이로 다시 잘림
- 결정(v3): 모델용 스키마에만 길이 상한(`structured.CAPS`, maxItems·maxLength — vLLM이 지킴 확인). 파일 요구사항 8·text 80자·evidence 100자, 공고 요약 핵심 요구사항 8·개요 300자 등. 꽉 채운 최악의 출력도 4,000토큰 안(테스트, 1.9자/토큰). 프롬프트에 같은 숫자, finish=length면 잘린 본문 없이 "더 짧게" 재요청. 25청크: 첫 시도 16/25 → **25/25**, 최대 출력 4,000 → 2,279토큰, 총 시간 −33%
- 결정(v4, 2026-11-13): 일정 `date`에 '협상 후' 같은 글이 들어가던 문제 → 스키마 pattern `YYYY-MM-DD` + 프롬프트 "연월일이 다 없으면 null". 형식만 강제하면 모델이 같은 날짜를 복사해 채움(확인)
- 결과(v4, `fp8-v4`): **형식 실패 0회**(두 번에 나눠 실행, 로그의 invalid_output 0 — v2b 42회). 원문 일치 91.6%(v2b 93.7%, 목표 95%). 필드 채움 일정 18·예산 19·요구사항 19·자격 14·평가 19. 인젝션 3/3 무시(g002 날짜만 달라짐). 추천 150건 첫 점수 **74초**(9호출, 목표 300초)
- 정답 초안2(2026-11-13, Claude 원문 대조, `draft_note`): 예산은 원문 사업비(부가세 포함 — G2B 값은 부가세 제외라 1.1배 차이), 방식은 "협상에 의한 계약", 원문 없는 5건 `no_text`. **같은 정답으로 다시 채점**: 예산 v2b 16/18 → v4 17/18, 마감일 0/16 → 6/16, 방식 12/18 → 11/18. 적합도 라벨도 바뀌어(high 2건) Spearman 0.68·P@5 0.2는 v2b와 비교하지 않는다
