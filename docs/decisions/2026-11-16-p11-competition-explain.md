# P11 공고별 경쟁 구도 · AI 해설 · 어시스턴트 도구 · 공동수급
- 명세 위치: §15.4(온디맨드·계약정보), §15.6(competition·explain), §15.7 '경쟁 구도', §15.8, §15.11 P11
- 결과: API `GET /bids/{bidId}/competition`·`POST /compare/{bizno}/explain`(SSE), 수집기 `--source contracts`,
  어시스턴트 도구 3개, 마이그레이션 0010(`bid_participant_fetches`, 사용 기록 `competition`·`compare_explain`),
  화면 공고 상세 탭('공고 정보'·'경쟁 구도', `?tab=competition`)과 비교 화면의 공동수급 파트너·AI 해설

## 결정
- **공동수급은 계약정보를 날짜 창으로 수집**: 계약정보는 등록일시·통합계약번호로만 조회된다(공고번호 조회 없음, API 문서)
  그리고 낙찰 응답만으로는 공동수급을 알 수 없다(probe 5번) → 'is_joint인 낙찰만 계약정보를 부른다'는 불가.
  `corpList` 방식이 단독이 아닌 계약만 `bid_joint_members`(주계약업체 포함)에 넣고, 같은 공고의 낙찰을 `is_joint=true`로
  맞춘다(낙찰·계약 어느 쪽이 먼저 와도). 신체계는 차수가 없어 `bid_ntce_ord=''`로 모든 차수와 잇는다
- **계약 호출량**: 실측 하루 약 5회(14일 67회) → 5년 백필 약 8,700회. 증분은 3일만, 백필은 한 번에
  `G2B_CONTRACTS_BACKFILL_CALLS`(100)회까지(상한 도달은 정상 종료). timer 순서: 낙찰 증분 → 계약 증분 → 낙찰 백필 → 계약 백필
- **온디맨드 개찰 결과**: 한 요청 새 호출 6회(재시도 포함, `client.call_cap`). 우선순위 이 공고(낙찰됐으면) → 보여 줄 과거 낙찰.
  불러온 공고는 0행이어도 다시 부르지 않는다. 같은 프로세스 동시 요청은 잠금으로 한 줄. 낙찰 몫 예산(`cache.source='opening_compt'`)
- **비슷한 사업**: 같은 수요기관(코드, 없으면 이름) 최근 500건 중 공고명 글자 2-gram 다이스 ≥ 0.2 또는 분야 태그 겹침.
  분포는 비슷한 낙찰 최대 50건의 낙찰률(G2B)·낙찰금액/추정가격 최소·중앙·최대(값 있는 것만). 기본 5건 표시(최대 10)
- **우리 참가 이력**: 이 수요기관 낙찰 수 + 불러온 개찰 결과 중 참가·낙찰 수('불러온 것만' 한계를 화면에 적음)
- **AI 해설 숫자 검증**(`app/analysis/explain_check.py`): 글의 숫자를 값·표시 자릿수로 읽어('7억' ±0.5억, '5.9억' ±0.05억,
  '1억 2천만원' 합) 입력 JSON의 수·문자열 속 숫자와 같아야 통과. '%'는 그대로 또는 비율×100. 'G2B'·'ratio_20'처럼
  영문에 붙은 숫자는 숫자가 아니다. 권유·예측 표현(투찰하·투찰가·가능성·확률·추천 등)도 막는다.
  실패 → 걸린 숫자를 알려 주고 한 번 다시 → 또 실패면 `explanation=null`(화면은 '해설을 보여 주지 않아요'와 표만).
  입력에서 `watched`(화면 상태)만 뺀다. 온도 0, 캐시 없음(누를 때만 만든다), 사용자당 분당 10회
- **어시스턴트 도구**: `search_companies`·`get_company_awards`(요약+최근 낙찰, 기본 10건)·`compare_companies`.
  라우터와 같은 함수(`app/awards/views.py`)·같은 스키마. 회사 미설정·없는 업체는 오류 안내문으로 돌려준다.
  업체 검색 도구도 `company_search` 사용 기록을 남긴다. 프롬프트에 '판정 그대로, 투찰가·낙찰 예측 안 함'을 더함
- 비교 응답에 `joint`(collected, us·them 파트너 상위 5)를 더했다. 계약정보 수집 전이면 '수집 중'

## 실제 LLM 점검 (Qwen3.5-9B FP8, 2026-11-17, `eval/competitor_llm.py`)
개발 DB 실제 낙찰 30일, 낙찰 1위 업체를 '우리'로 두고 레이더 상위 6곳. 결과 `eval/results/2026-11-1{6,7}_competitor_llm_fp8*.json`
| | 처음(가짜 LLM 기준 구현) | 고친 뒤(v5) |
|---|---|---|
| 해설 첫 시도 통과 / 재시도 뒤 / 일부 문장 뺌 / 해설 없음 | 1 / 5 / – / 0 | **4 / 0 / 2 / 0** |
| 기간 | '2021년 11월부터'(요청 기간) | 실제로 센 기간 |
| 비교 도구에 업체명만 줌 | 사업자번호를 되물음 | 이름으로 찾아 비교 |
| 투찰가 질문 | 거절 | 거절 |
- 실제 모델에서 나온 것과 고친 것: 요청 기간을 기간으로 씀 → 모델 입력에서 period는 센 범위만. 억 단위 변환 오류
  ('1,208,634,929원' → '12억 8,634만') → 금액은 쉼표 넣은 원 단위로 쓰게 하고, 검증기는 반올림·버림 표기 허용,
  '…만 9,000원' 끝자리 합침, ISO 날짜의 날을 읽음. 글로 쓴 배수('두 배') 차단. 목록 개수 세기('파트너 5곳')는
  두 번째에도 남아 → **두 번째도 걸리면 걸린 point만 빼고**(요약이 깨끗하고 2개 이상 남을 때) 보여 줌.
  재시도 안내에 문제 문장을 인용. '14 건' 띄어쓰기는 서버가 붙임
- 어시스턴트: 처음엔 낙찰 도구를 쓴 답도 스트리밍하고 틀리면 안내만 붙였으나, 실제 모델이 '1692억'(실제 169억)·
  '12억 8천만'·'2배 이상'을 계속 써서 **2026-11-17 사용자 결정으로 바꿈**: 낙찰·경쟁사 도구를 쓴 뒤의 답은 모아 두고
  (상태 '답을 만들고 숫자를 조회 결과와 맞춰 보고 있어요') 검증 → 틀리면 문제 줄을 인용해 한 번 다시(도구 금지) →
  또 틀리면 걸린 문장만 빼고 안내(남는 게 없으면 고정 안내). 틀린 숫자는 화면에 나가지 않는다. 도구 결과의 period도
  센 범위만 준다(비교 답이 '2021-11-18부터'라고 씀). 다시 만들 때 도구 호출을 글로 쓰는 경우(`<tool_call>…`)는 지우고 첫 답을 씀
- 비교 질문 5곳 재점검(`2026-11-17_competitor_llm_fp8-v6.json` + 추가 5회): 화면에 나간 숫자 중 도구 결과에 없는 것 0,
  첫 시도 통과 1 / 다시 만든 뒤 3 / 문장 뺌 1. 대신 비교 답은 다 만들어질 때까지 17~27초 기다린다
- **계약 백필 기간**: 사용자 결정으로 5년 유지(하루 100회면 약 3달, 공동수급 표시는 수집된 만큼만)
