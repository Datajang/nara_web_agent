# LLM 동시 호출 상한(LLM_MAX_CONCURRENCY) 4 → 8 검토
- 명세 위치: §5.5·§8.2 `LLM_MAX_CONCURRENCY`(기본 4 [가정])
- 계기: 외부 LLM API 전환 검토(사용자, 2026-11-24). 운영 사용량(`deploy/sql/llm_usage.sql`, 14일):
  LLM 요청 7건·하루 최대 21회, 최대 동시 1. 분석 p50 264초·최대 325초, 분석 1건 = 호출 9.5회·출력 약 12,600토큰
- 확인(코드): 요약 map은 `asyncio.gather`로 청크를 한꺼번에 보내고 전역 세마포어가 4개로 막는다(`pipeline/summarize.py`).
  reduce·분석은 그 뒤 한 번씩 순서대로 → 상한은 map 구간에만 효과
- 확인(용량): vLLM은 `--max-num-seqs 8`. FP8 KV 캐시 59,136토큰이지만 Qwen3.5는 일부 층만 전체 어텐션이라
  vLLM 계산 '32K 요청 최대 동시성 6.82배'(P0-b). 청크 12,000 + 출력 약 2,000토큰 × 8개는 들어간다
- 확인(속도): 짧은 입력 합계 4개 92·8개 177토큰/초(P0-b), 긴 실제 청크 3~4개 64~68토큰/초(P3a-2). 8개 긴 청크는 미측정
- 추정: map 구간만 빨라져 분석 264초 → 약 200~230초(약 15~25%). 남는 시간은 reduce·분석의 단일 요청 속도(약 24토큰/초)
- 위험: 요청당 속도가 떨어져 긴 출력(4,000토큰)은 `LLM_TIMEOUT_S` 360에 가까워질 수 있다(실측 map 출력 1,043~2,113).
  분석 하나가 8칸을 다 쓰면 다른 사람 어시스턴트가 기다린다 — 4일 때도 청크 4개 이상이면 같다
- 실측(운영, 2026-11-24 23:47~23:50 KST, 상한 8): vLLM KV 60,192토큰·32K 동시성 6.91배. 청크 3개 공고라 동시 최대 3
  (상한 효과 없음): 217.7초, 같은 크기 공고 상한 4는 202.6초. vLLM 로그 구간 — map 3개 약 85초(합계 67토큰/초,
  요청당 약 22), reduce 약 90초·분석 약 30초(각 23.5토큰/초 단독). KV 사용률 최대 9.5%, 대기 거의 없음
- 해석: 분석 시간의 약 60%가 순서대로 도는 reduce·분석의 단일 요청 속도. 동시 3개에도 요청당 속도는 거의 그대로라
  상한을 올려도 손해는 없고, 이득은 청크 5개 이상 공고(map 3바퀴 → 2바퀴, 약 60~80초 추정)에만 있다
- 결정: 운영 `LLM_MAX_CONCURRENCY=8` 유지(사용자 적용, 코드 기본값 4는 그대로). 큰 공고 효과는 사용량 기록으로 확인
- 다음: 단일 요청 속도를 올리는 쪽 — 외부 API(Gemma) 골든셋 비교, MTP 추론 가속(미시험), reduce 출력 줄이기
